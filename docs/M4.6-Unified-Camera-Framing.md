# Unified camera framing for all eight levels

Let Unity recompile and press Play in the existing FeedbackCampaign. No Apply,
scene generation or YAML edit is required. All eight levels now use the same
adaptive close-framing policy; the approved Level 7/8 camera position and size
are preserved exactly at the default setting.

## Previous inconsistency

The runtime previously selected three profiles:

- Levels 1–4: fixed 6.25 reference size, widened for tall portrait screens.
- Levels 5–6: fit the entire conservative world AABB, including fully departed
  multi-cell blocks and burst margins; retain the minimum reference size.
- Levels 7–8: tighter continuous presentation bounds, then the approved 1.25
  physical zoom with playable-board/HUD constraints.

Consequently Level 6 reserved the full outward side-exit width and occupied only
68.3% of the viewport, while Levels 7/8 used the accepted cosmetic clipping policy
and occupied approximately 90%. Merely applying 1.25 physical zoom to every level
would oversize the smaller trays and still undersize Level 6.

## Shared adaptive policy

`BoardFraming.AdaptiveZoom` now calculates the close composition from the actual
authored tray projection, playable envelope, camera basis/aspect and safe area.
`PortraitCameraFit` applies it for every registered level, without a level-number
or board-height exception in the close-framing policy.

1. Target **90% of safe-area width**, with a **90.5% upper limit**. The projected
   tray width determines the requested orthographic size. The tray renderers are
   read from the existing scene through the theme's tray material.
2. If the prior 1.25 reference composition already lies between **89.5% and 90.5%**
   of safe width, keep its position and size. This dimension-independent tolerance
   preserves the approved Levels 7/8 exactly instead of nudging them by a few pixels.
3. Otherwise center the playable/tray bounds in the same HUD-safe gameplay region.
   Enforce complete board, selected-block/contact-shadow, gate-floor and peak Gate
   Glow bounds. The minimum size comes from projected width and height, never an
   exit trajectory. A larger required size takes precedence over width utilization.
4. Hard gameplay margins remain **32 reference pixels per safe side, 72 below,
   316 above** (280 HUD, 12 offset, 24 separation), with the existing CanvasScaler
   scaling and 0.2% numeric safety margin. Camera orientation, orthographic
   projection, depth and every world geometry transform remain unchanged.

The control range is still **1.00–1.25**, with **1.25 as the default**. The Inspector
label is now **Gameplay Zoom**. The existing public `LargeBoardZoom` property and
private configuration key remain for compatibility. At 1.00, historical reference
frames remain available; if a narrow/short safe area makes that old endpoint closer
than the adaptive composition, it is normalized to the safe close frame. This
prevents Plus from unexpectedly zooming out.

Intermediate settings interpolate physical scale and camera placement toward the
computed close frame. They are not a common physical multiplier across levels.
For example, at 1080x1920 the actual default scale change is **1.054688x** for
Levels 1–4, **1.102174x** for Level 5, **1.316843x** for Level 6 and **1.25x** for
Levels 7/8. At 1080x2400 the Level 5/6 changes are **1.110430x / 1.326707x**.
The existing key log reports both the requested control and this effective scale.

## Exits, interaction and Editor controls

The accepted policy is unchanged: only successfully removed blocks may travel
partially outside the viewport during their original outward animation. The same
continuous fragment envelope constrains the cosmetic burst root in XZ at birth,
preserving original Y, relative paths, rotations, 10-fragment count, materials,
0.18/0.30-second durations, authoritative end anchors, occupancy and Win sequencing.
The visibility constraint now also runs at the normalized 1.00 endpoint whenever
a valid calculated viewport is available; if the whole burst already fits, its
origin stays unchanged. No SoftCubeBurst or motion implementation was edited.

Plus/Equals, Shift+Equals and numpad Plus/Minus continue in the existing Editor-only
focused Game View/Input System callback. Values persist across level replacement,
Retry and Next without PlayerPrefs. They reset between Play sessions. Requests
wait for selected drags and active exits to finish; an animation never changes
framing bounds. Player/Android builds contain no QA key handler or override API.
No new UI controls, objects, dependencies or setup menus were added.
